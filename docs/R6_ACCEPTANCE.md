# TechSignal R6 验收报告：从「看案例」到「自己建研究」

- 日期：2026-11-04
- 仓库：`previteoberle-cloud/techsignal`，分支 `feature/r6-research-workflow`（基于 `main` v0.5.0），版本号 0.6.0
- 旧 Fork（`previteoberle-cloud/changedetection.io`）：本轮**没有任何改动**

## 一句话结论

不会编程的人现在可以在浏览器里**用文字新建一个研究项目**，连接自己运行的 changedetection.io，**确认后**建立监测，**手动检查一次**并看到逐条解释的研判结果；判断修改有版本记录，后台不会改写判断。

模型层已支持「一次调用、逐条假设给建议」，建议要经过规则校验，失败就保守降级。**但本轮没有调用任何真实大模型**：没有获得授权的模型服务。所有模型相关测试使用 Mock 或本地协议桩，真实模型测试标记为 **BLOCKED**。

## 二、P0：新建研究项目

**用户要填的内容（全部是普通文字）：**
- 公司或主题名称（可加别名）
- 技术领域或核心研究问题
- 当前研究判断
- 一条或多条关键假设，每条可以写「支持信号」「削弱信号」
- 要监测的公开网址（每行一个，可附说明），并为每个网址选择来源类型
- 可选的主题词

系统把这些文字转换成现有的 `Thesis` / `SourceProfile` 模型并做校验。用户不写 JSON、Python 或正则。信号词按字面匹配：
- 经过 `re.escape` 转义，不区分大小写；
- 拉丁字母或数字开头、结尾的词会检查边界，所以「70B」不会命中「170B」。

页面明确写着「**不是语义理解**」。没有填写信号词的假设，相关变化只会被标为「待人工判断」。

**存储：**
- 默认路径是 `~/.techsignal/projects`，可用环境变量 `TECHSIGNAL_PROJECTS_ROOT` 修改。
- 存储目录如果位于仓库的 `cases/` 或 `demo/` 里面，会直接拒绝。
- 每个项目一个目录，目录名是 `p-` 加 12 位随机十六进制数。

**可靠性：**
- 写文件先写临时文件，再用 `os.replace` 原子替换。
- 跨进程锁基于 `mkdir`。持有锁的进程崩溃后，超过 120 秒的锁可以被接管。
- 每次保存都生成 `versions/vN.json`，旧版本永不改写。
- 保存时必须说明是基于哪个版本修改的。中途别人已保存的话，本次保存会被拒绝，不会覆盖（乐观并发）。
- 草稿可以先保存、之后补全。已创建的项目不能退回草稿。草稿不会生成流水线输入。

**输入校验：**
- 网址只允许 http 或 https。
- 拒绝带用户名或密码的网址、localhost、内网和保留 IP（包括云元数据地址 169.254.169.254）、`.local` / `.internal` 等内部域名、单段主机名、无效端口和非法域名。
- 拒绝重复项目名。判断是否重复时，忽略大小写、空格和全角半角差异。
- 项目编号、运行编号都要通过格式校验，并检查解析后的路径是否仍在项目目录内；指向目录外的符号链接会被拒绝。
- 会去掉控制字符和零宽字符。
- 有长度和数量上限。
- 同一个词同时被写成支持和削弱信号时会报错。

**展示：**
- 没有监测数据时显示「尚无监测变化」，并说明不会显示示例或伪造数据。
- 名称或别名不超过 3 个拉丁字母时，会提示容易误命中其他公司（见评测 E09）。

**测试：** `tests/test_r6_projects.py` 共 59 个，`tests/ui/test_r6_projects_app.py` 共 9 个（Streamlit AppTest）。覆盖：
- 创建、读取、生成的输入能通过现有模型校验、生成的研究判断能驱动真实流水线；
- 非法网址（17 种）、缺字段、过短或过长的词、控制字符、重复名称（含并发创建）、改名撞名；
- 过期编辑被拒、5 个线程同时编辑只有 1 个成功；
- 路径穿越和符号链接；
- 写入失败后保留旧版本，且重试能成功；创建失败不留残留；文件损坏只影响该项目；接管陈旧的锁；
- 示例案例目录的哈希在所有操作前后保持不变。

**UI 测试中发现并修复的问题：** 在别的窗口保存了新版本后，表单会悄悄换成新版本的内容，用户正在编辑的修改就丢了。现在表单固定在开始编辑时的版本，保存时会被拒绝，并提供「放弃本次修改，载入最新版本」按钮。

## 三、P1：连接 changedetection.io，手动检查一次

整个流程在「监测与评估」页面，**只在用户点击按钮时**访问外部服务：

1. **连接**：只读请求，读取 systeminfo 和已有的监测项。
2. **规划**：对项目里的每个网址，已有同网址的监测项就关联，不重复创建；没有才新建。
3. **建立监测**：必须勾选确认，按钮才能点击。只会创建本项目中、并且重新通过网址校验的网址；被篡改的计划会被拒绝。关联关系写入 `monitor.json`，其中**只保存服务地址，不保存 API key**。一个项目只能关联一个 changedetection.io 实例。
4. **立即检查一次**：
   - 请 changedetection.io 重新抓取并等待完成，然后读取游标之后的 ChangesReport；
   - 第一次抓取只建立基线；
   - **没有新快照，或者前后没有实质差异时，只记录「本次没有新的变化」，不运行研判，也不生成任何结果**；
   - 有实际变化时，用真实流水线研判（命令行在线模式加 `--track-history`），结果写入 `state/`，并复制一份到 `runs/<编号>/`，同时保存当时的研究设定版本和研究判断文件。之后再修改判断，也不会改变已有批次的展示。
5. 检查记录写入 `checks.jsonl`。整个流程**从不写 `project.json`**，测试会逐字节核对。
6. 没有 changedetection.io 时，工作台照常运行，并提示需要这个外部服务。
7. 没有调度、没有通知（属于 R7）。

**浏览器验收中发现并修复的问题（真实 changedetection.io 0.60.10）：**
- 现象：第二次检查明明有真实变化，却报告「没有新的快照」。
- 原因：上游 `worker.py:157` 在检查**开始时**就设置 `last_checked`，快照保存之后才在 `worker.py:627` 增加 `check_count`。原来的等待条件看的是 `last_checked`。
- 修复：改为等待 `check_count` 增加。
- 新增反例测试：在旧代码上失败，在新代码上通过。

**测试：**
- `tests/test_r6_monitor.py` 共 21 个，使用离线替身 `tests/fake_cdio.py`，它模拟上游的时间窗口语义，以及「先设置 last_checked、后保存快照」的时序。
- UI 流程测试 1 个。
- `tests/integration/test_r6_project_live.py` 共 2 个，使用**真实的 changedetection.io**：
  - 本地测试页：新建项目 → 建立监测 → 基线 → 页面变化 → 规则判定「削弱」，A 级证据；
  - 真实公开页面（tenstorrent/tt-metal 的 main 分支 README）：连续两次检查，都**没有产生研判**。
  - 两个测试在本地和 CI 都通过。

## 四、P2：模型层（在 `OpenAICompatibleProvider` 基础上增量开发）

- **新协议 `multi`**：一次调用，按假设逐条返回结果。每条包括：
  - `change_kind`，取值为新事实 / 删除记录 / 否认 / 文档重排 / 无关 / 无法判断；
  - 方向、理由、引用的证据编号和置信度。

  提示词把网页内容标注为数据，并说明其中的指令不是给模型的。
- **逐条校验**：
  - 返回结构正确；
  - 假设确实存在；
  - 引用的证据必须属于本次变化；
  - 给出方向时必须引用证据；
  - 同一假设不能给出相互矛盾的结论。

  不合格的条目单独按规则保守处理，合格的条目仍然保留。
- **定向门槛**：只有「新事实」才允许给出方向，并且还要满足三个条件：
  - 差异里确实有新增内容；
  - 规则层没有发现否定语境；
  - 规则层命中的信号方向与模型一致。

  此外，变化内容中如果有疑似针对模型的指令，模型的方向建议会被拦截（复用 R3 的检测）。证据等级门槛照常生效。被门槛拦下的方向**只记录在 `model_suggestion` 里**，不参与冲突处理和跨批次比较。
- **失败和超时**：调用失败、超时、格式错误、HTTP 错误、超过调用上限时，都降级为「证据不足」，运行不中断。
- **限额**：
  - 输入长度上限 `TECHSIGNAL_LLM_MAX_INPUT_CHARS`，默认 6000 字符，超出部分在结果里注明；
  - 每次运行的调用上限 `TECHSIGNAL_LLM_MAX_CALLS`，默认 20 次；
  - 超时 `TECHSIGNAL_LLM_TIMEOUT`，默认 30 秒。
- **用量记录**：记录调用的发出、成功、失败和因上限跳过的次数，以及被截断的输入数。服务报告了 token 用量时才记录，没报告时速览写明「服务未报告用量」。
- **三类信息分开保存**：
  - `model_suggestion`：模型的原始建议；
  - `direction`：规则校验后的最终结论；
  - `review_status`：人工复核状态。
- **来源标注**：只有至少一次调用成功时，才标为 `real_model`；配置了模型但没有成功调用时，标为 `real_model_unused`，速览会如实说明。
- **兼容性**：R1–R5 的单一判断协议和全部已有输出**逐字节不变**（新增字段在没有使用时不输出）。

**真实模型：** 没有获得授权的服务，**没有调用**。`tests/test_r6_real_llm.py` 标记为 BLOCKED。以后只需设置 `TECHSIGNAL_LLM_BASE_URL`、`TECHSIGNAL_LLM_MODEL`、`TECHSIGNAL_LLM_API_KEY` 和 `TECHSIGNAL_REAL_LLM_AUTHORIZED=1` 就能运行，**不需要修改业务代码**。

为确认这一点，我用本地「回声协议桩」（不是模型）设置这些环境变量，空跑了一次，测试路径完整执行。这次空跑**不是**真实模型结果，也没有写入任何文档数字。

**测试：** `tests/test_r6_model_layer.py` 共 27 个协议桩测试，另有项目流程中使用已配置模型服务（协议桩）的测试 1 个。

## 五、P3：判断来源与透明度

「研判结果」页面的每条判断依次显示：
- 判断来源：确定性规则 / 模型服务建议（已通过校验，附服务名）/ 模型建议被拒绝 / 模型调用失败已降级 / 超出调用上限 / Mock 或协议桩 / 规则无法判定；
- 发生了什么：关键的新增或删除内容；
- 「为什么这样判断」（展开查看）：规则依据、模型建议原文、逐项检查（引用校验、证据等级、变化类型、降级原因、冲突处理，以及「研究判断保持不变」）；
- 仍未解决的问题、建议动作、复核状态；
- 引用的证据（展开查看）。

模型永远不会改写研究结论。

**由浏览器截图发现并修复的两处显示问题：**
- 本地测试页的结果曾被标为「真实公开资料」。现在只要项目监测了非公开地址，就标为「虚构测试数据」。
- 理由里曾显示内部正则 `(?i)推迟`。现在按用户输入的原文显示。手写规则的显示不变。

## 九、仍然存在的限制（R7 之前）

- **没有调用过真实大模型**，没有任何模型准确率数字。
- **没有持续监控**：没有调度、通知或失败重试，只能手动「检查一次」。
- 规则层有两类已知错误（远距离否定、短别名）。规则先于模型判断，所以模型无法复核规则的误判。
- 新建项目暂不执行补证，补证白名单仍需手写 JSON。
- 工作台没有登录与权限，只面向本机使用。网址校验基于主机名，公开域名解析到内网地址的情况，要靠 changedetection.io 自身的默认防护。
- 只有一个真实公开案例；R6 评测集是虚构案例，标注由本项目编写。
