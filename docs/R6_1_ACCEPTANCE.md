## 二、P0-01：否定语境

**原因：** `rules.py` 只检查信号词前面固定 4 个字符内有没有否定词。

**修复：** 不是把窗口改大，而是改为**按分句判断**：
- 用句号、问号、分号、换行、表格竖线和转折词（「但」「然而」「however」）把句子切成分句；
- 信号所在的分句里，**不论前后、距离多远**，只要有否定、辟谣或疑问表达，信号就判为「不明确」，规则不给方向。
  - 中文否定词包括「没有、并未、并非、不、无法、否认、辟谣、谣言、不实、是否、吗」等；
  - 英文包括 not、no、never、deny、whether、n't 等；
- 双重否定（同一分句有两个以上否定表达）**不尝试解析**，直接判为不明确；
- 问号结尾的分句判为不明确；
- 「未来、不断、不仅、不同、不久、不过」等词不算否定。

**结果：**
- E05 和 8 个变体都不再给出方向；
- 否定在另一句话里（E17）、先否认一件事再转折承认另一件事（E19）、普通的支持或削弱语句，仍然给出正确方向。

**说明：**
- 「传闻」「据传」**不算**否定。最初我把它们也算进去，结果虚构演示的输出（`demo/output`）改变了，而且这不属于否定问题。这类表述由来源等级门槛处理。所以撤回了这项改动，演示输出保持逐字节不变。
- 规则命中的否定原本就能识别的情况，说明文字仍是「（前有否定词）」，不改变历史输出。

## 三、P0-02：企业实体误匹配

**原因：** `match_theses` 用 `e.lower() in haystack` 做子串匹配。

**修复：**
- **英文和数字按完整单词匹配**：名称两端是英文字母或数字时，紧挨着的字符不能也是英文字母或数字。
  - 「XH」不会命中「XHTech」「XHS」「AXH」「XH2」，「Arm」不会命中「Armstrong」；
  - 「XH半导体」会命中（中文字符算边界）。
- **短简称降级**：如果只命中了短简称、没有出现全称，规则不给方向，提示「需要人工确认是否为研究对象」。短简称包括：
  - 3 个以内英文字母或数字的别名，自动认定；
  - 用户在新字段「易混淆的简称」里标记的别名。
- 同样的检查也加在模型路径上：模型不能把只命中简称的变化判为有方向。
- **没有禁止简称**：
  - 主名称永远视为可靠；
  - 「星衡」这类正常的中文简称默认可用，不会自动降级；
  - 只命中简称时仍会生成待核实事项，不会被丢掉；
  - 页面会提示过短的简称。

**结果：**
- E09 变为「无关」；
- E20（只出现简称 XH）变为「待核实」；
- E21 中的「XH-Power」：连字符算作边界，所以仍然会命中简称，结果是「待核实」，属于保守、不是错误。这是当前规则的局限，已写入报告。

## 四、P0-03：来源身份与证据等级

**原因：** 用户在表单里选择「公司官方」，系统就把该网址当作 A 级来源，而且表单默认选的就是「公司官方」。

**修复：**
- **区分声明与确认。** `SourceInput.source_type` 只表示用户的声明；新增的 `confirmation` 字段记录确认后的类型、确认人、确认时间和确认依据。
- **表单默认值改为「未分类」。**
- **未确认来源最多按 C 级处理**：声明为官方、监管、媒体或第三方分析时按 C 级，声明为论坛或未分类时按 D 级。原有的等级门槛规定只有 A、B 级可以单独定向，所以未确认来源永远不能单独支撑支持或削弱判断。监管文件和媒体同样需要确认。
- **新增「来源确认」页面：**
  - 选择确认后的类型，填写确认人和确认依据（4 到 300 个字）后确认；
  - 每次确认生成一个新的项目版本，并显示在「修改记录」里；
  - 确认可以撤销，撤销也会生成版本；
  - 表单编辑不能伪造确认；修改网址列表时，没有变化的网址保留确认，新网址一律未确认。
- **界面显示：** 每个来源都标明「已确认：公司官方｜A 级｜确认人，日期」或「未确认（你声明为……）｜按 C 级处理」；证据上标注「来源未经确认」；概况页提示还有多少来源未确认。
- **已保存项目的迁移：**
  - R6 保存的项目没有确认记录，被视为全部未确认；
  - 打开项目或每次检查前，会按当前项目和当前规则**重新生成**研判输入；
  - 等级变化写入 `migrations.jsonl`（例如「A → C」），界面会提示并在「修改记录」中列出；
  - **研究判断文件和版本号都不变，任何来源的等级都不会被提高**；
  - R6 时期已经生成的研判批次保留当时的记录，不追溯修改。
- **示例案例不受影响：** 仓库中的真实 Tenstorrent 案例使用的是人工维护并提交的来源登记表，不受这条规则影响。

## 七、浏览器验收中发现并修复的两个界面问题

用真实 Chromium 加真实 changedetection.io 0.60.10 实测：

1. **离开「监测与评估」页再回来后，地址和 API key 变成空的，下一次检查因 403 失败。**
   - 原因：Streamlit 服务端会丢弃未显示的输入框的值。
   - 修复：地址和 key 保存在本次浏览器会话的内存里，并在回到页面时恢复。仍然不写入任何文件，测试会核对。
   - 说明：我新增的 AppTest 回归测试在旧代码上**也能通过**，因为测试工具不会丢弃这些值，所以它不能复现这个问题。真正的复现和修复验证都由浏览器脚本完成，测试文件里也写明了这一点。
2. **新的检查产生研判后，「研判结果」页仍停留在之前选中的旧批次。**
   - 修复：产生新批次后，结果页默认显示最新批次。

浏览器脚本 `docs/screenshots/r6_browser_check.js` 新增的步骤：
- 来源未确认时，真实变化只得到「证据不足」，并标注「未确认来源」；
- 在「来源确认」页确认来源，记录「王研究员」和确认依据；
- 离开页面再回来，API key 仍在；
- 第三次检查得到「削弱」，跨批次变化为「证据不足 → 削弱」；
- 修改记录同时显示 v1、v2（确认来源）和 v3。

全部检查通过，没有横向溢出，没有页面错误。新增截图为 `docs/screenshots/r61_10`、`r61_11`、`r61_12`，`r6_*` 截图已更新。

我还修正了脚本本身的一个误判：原来的脚本在页面中查找文字，会把检查记录中的旧消息当作本次结果。现在只读取本次检查的提示框。

## 十、R7 是否可以安全进入

本轮目标中的三个 P0 风险已经处理，没有剩下已知的确定性方向错误。**我的判断是：可以进入 R7，但应先满足以下前提**：

1. **人工待核实事项会增加**：R7 的通知要按「待核实」和「有方向」分级，避免通知过多。
2. **来源确认是人工步骤**：自动运行的项目必须先完成来源确认，否则只会产生「待核实」。建议 R7 在开启自动运行前强制检查。
3. **规则的已知局限**：
   - 同义改写识别不了；
   - 「传闻」类措辞不单独处理；
   - 连字符相连的英文名（如 XH-Power）只能降级为待核实，不能区分是否为同一主体；
   - 模型不复核规则的明确结论。
4. **真实模型仍然 BLOCKED**：R7 不应依赖模型。
