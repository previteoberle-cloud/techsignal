# 研究判断的决策规则：规则、模型与安全闸门（R6.1）

本文说明 TechSignal 现在怎样作出「支持 / 削弱 / 证据不足 / 无关」的判断，以及真实模型将来的位置。描述的是**代码已经实现的行为**；标注「将来」的部分尚未实现。真实模型**从未被调用过**（没有获得授权的服务）。

## 处理顺序

```
变化内容
  → 1 降噪、去重
  → 2 主体识别（这条变化说的是不是研究对象）
  → 3 规则判断：明确 / 无关 / 不明确
  → 4 仅对「不明确」：可选的模型建议
  → 5 硬性闸门：证据等级、来源冲突、跨批次冲突
  → 6 建议动作
```

第 6 步只给出建议，**任何一步都不会修改研究判断本身**。

## 1. 哪些规则结果可以直接作为最终方向

规则只有在以下**全部**满足时，才给出「支持」或「削弱」：

1. 命中了研究对象的**全称或可靠别名**。只命中短简称（3 个以内的英文字母或数字，或者用户标记为「易混淆的简称」）不算。英文和数字按完整单词匹配：「XH」不会命中「XHTech」，「Arm」不会命中「Armstrong」。
2. 信号词出现在**新增**内容里。只在删除内容里出现的信号不算。
3. 信号所在的**分句**里，没有否定、辟谣或疑问表达。不论这类表达在信号词之前还是之后、隔了多远都算。
   - 分句按句号、问号、分号、表格竖线和转折词（「但」「然而」「however」）切分；
   - 「未来」「不断」「不仅」这类词不算否定。
4. 同一条变化里，所有信号指向同一个方向。
5. 证据来源为 **A 或 B 级**。对用户新建的项目，只有**经人工确认身份**的来源才可能是 A 或 B 级（见第 5 节）。
6. 与同一批次的其他证据、与历史批次的证据，都没有方向冲突。

即使满足全部条件，结论也只是「建议研究负责人复核」，研究判断不会被改写。

## 2. 哪些结果强制进入「待核实」

以下任何一种情况，结果都是「证据不足，待核实」：

- 信号所在分句里有否定、辟谣或疑问；有多个否定（双重否定）也一样，规则**不尝试解析**；
- 信号只出现在删除内容里；
- 同一变化里同时出现支持和削弱信号；
- 只命中了短简称或易混淆的简称，需要人工确认主体；
- 来源是 C 或 D 级。这包括用户声明为官方、监管、媒体，但**未经确认**的来源；
- 同批次或跨批次存在方向相反的证据（系统不自动裁决）；
- 提到了研究对象和主题词，但没有命中任何信号词；
- 模型调用失败、超时、输出格式错误、超过调用上限、引用了不存在的证据，或者对同一假设给出相互矛盾的结论。

## 3. 真实模型将来在什么情况下参与

**现在：** 模型只处理规则判为「不明确」的变化，给出逐条假设的建议。模型建议要经过：

- 结构校验；
- 假设存在性校验；
- 引用校验（引用的证据必须属于本次变化）；
- 变化类型门槛（只有「新出现的事实」才允许定向）；
- 与规则信号的一致性校验；
- 否定语境校验；
- 主体（简称）校验；
- 提示注入校验；
- 证据等级门槛。

任何一项不通过，模型的方向建议都只保留在 `model_suggestion` 里，不会成为结论。

**将来（R7 之后，需要授权的模型服务和评测数据）：**

1. **复核规则的「明确」结论**。目前规则先判断，模型看不到规则判定为明确的变化，所以规则的误判没有第二道检查。R6 评测中规则层的两个错误（E05、E09）就属于这一类，本轮是通过收紧规则修复的。将来模型可以对规则的明确结论做**只降不升**的复核：模型只能把结论降为「待核实」，不能翻转方向，也不能把「待核实」升为有方向的结论。
2. **在人工确认之前，先给出意见**，例如简称是否指研究对象、否定句的真实含义。这类意见只是给人看的提示，不进入结论。
3. 是否启用，要先在评测集上用真实模型实测，并公开整改前后的数字。

## 4. 如何防止模型覆盖硬性证据和安全闸门

- 研究判断文件只能由人保存，监测和模型流程只读，有逐字节测试保证。
- 硬性闸门在模型**之后**执行，模型不能绕过：
  - 证据等级门槛（C 或 D 级不能单独定向）；
  - 来源冲突、跨批次冲突（不自动裁决）；
  - 来源确认（用户新建的项目中，未确认来源最多 C 级）。
- 被闸门拦下的模型方向**不计入**冲突处理和跨批次比较，避免一个被拒绝的建议影响后续判断。
- 模型建议、最终结论和人工复核状态分开保存。界面上的「判断来源」只有在模型调用真正成功时，才显示为模型。
- 网页内容在提示词中明确标为数据；如果疑似包含针对模型的指令，模型的方向建议会被拦截。
- 每次运行都有调用次数、输入长度和超时上限；超出时按「待核实」处理。

## 5. 没有模型时如何保持安全运行

这是当前的默认状态：

- 规则无法判定的变化都列为「待人工判断」，并给出具体问题。**不会猜测方向**。
- 评测中规则层整改后**没有方向错误**，原来的错误都变成了「待核实」。代价是更多事项需要人工处理，这一点在评测结果中如实列出。
- 来源确认、简称确认都由人完成，并且有版本记录。
- 没有 changedetection.io 时工作台照常可用；没有新快照时不会产生任何研判。

## 来源身份：用户声明与确认的区别（R6.1）

| | 用户声明 | 人工确认之后 |
|---|---|---|
| 作用 | 记录用户认为它是什么来源 | 记录有人核对过来源身份 |
| 证据等级 | 官方、监管、媒体、第三方分析 → **C 级**；论坛、未分类 → **D 级** | 按确认后的类型分级：官方 A、监管或媒体 B、第三方分析 C、论坛或未分类 D |
| 能否单独定向 | 不能 | A、B 级可以 |
| 记录 | 项目版本 | 确认人、确认时间、确认依据，并生成新的项目版本；可以撤销，撤销同样留有记录 |

补充说明：

- 修改网址列表时，**没有变化的网址保留确认，新网址一律未确认**。表单不能伪造确认。
- R6 保存的项目：项目文件里没有确认记录，所以检查前会**重新生成**研判输入。原来的 A、B 级降为 C 级，每次调整都写入 `migrations.jsonl`，界面上也有提示。研究判断和版本号不变。任何来源的等级都**不会被提高**。
- R6 时期已经生成的研判批次保留当时的记录，不会追溯修改。
- 仓库中的真实案例（Tenstorrent）使用的是人工维护并提交的来源登记表，不受这条规则影响，输出逐字节不变。
